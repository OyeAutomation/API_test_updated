# API Security & Validation Testing Framework

A CLI-based Python tool for QA engineers that automates manual API security and validation testing. Takes a curl command + optional encryption profile, runs header tests, detects mandatory payload keys, applies a configurable validation/vulnerability matrix, and produces an Excel report.

## Setup

```bash
pip install -r requirements.txt
```

## Quick Start

### 1. Seed default test cases

```bash
python -m src.cli seed-test-cases
```

Creates `test_cases/default_test_cases.xlsx` — the editable bank, generated from the built-in universal suite (38 cases).

### 2. Launch the GUI

```bash
python -m src.cli gui
```

The GUI supports single-curl and batch modes, crypto profiles (request/response),
an **API Profiles Dir** field (archetype-driven test selection + contract
evaluation — auto-matched per curl by file stem, then URL substring), and a
summary of vulnerabilities accepted / contract defects.

### 3. Validate a curl command

```bash
python -m src.cli validate-curl --curl "curl -X POST https://api.example.com/users -H 'Content-Type: application/json' -d '{\"name\":\"test\"}'"
```

Or from a file:

```bash
python -m src.cli validate-curl --curl-file request.curl
```

### 4. Run the full test suite

```bash
python -m src.cli run --curl-file request.curl --output reports/report.xlsx
```

With a crypto profile:

```bash
python -m src.cli run --curl-file request.curl --crypto-profile config/crypto_profiles.yaml --profile-name default --output reports/report.xlsx
```

### 5. Run against the local mock server

```bash
# Start the server
python mock_server/app.py

# In another terminal, run the tests
python -m src.cli run --curl-file test_register.curl --output reports/report.xlsx
```

## Rate Limits & IP Blocks

Real APIs often rate-limit or temporarily block an IP that sends many
requests. The suite detects this and **pauses with a prompt** instead of
hammering the endpoint (which is what turns a temp limit into a full
block).

**Detection:** a `429 Too Many Requests` response, or a `403` whose body
contains block markers (`blocked`, `rate limit`, `access denied`,
`captcha`, ...). Detection runs on every request path, including
mandatory-field probing.

**Pause prompt (CLI and GUI — default ON):**

- CLI: prints the endpoint, status and block count, then asks:
  - `Enter` — resume with the current delay
  - `d` — double the delay between requests and resume
  - `<number>` — set a custom delay in ms (e.g. `2000`) and resume
  - `c` — cancel the run
- GUI: a modal dialog shows the same info with a delay field and three
  buttons — `Resume`, `Resume & Apply Delay`, `Cancel`. An applied delay
  also updates the GUI "Delay (ms)" spinbox for the next run.
- Cancelling stops the run gracefully (loops, duplicate-submit, batch
  mode) — it never leaves the API in a half-tested state.

**Headless (tests, scripts, CI):** without an interactive handler the
suite never hangs — it logs a warning, honors the API's `Retry-After`
header (capped at 30 s), and continues.

**Controls:**

```bash
python -m src.cli run --curl-file request.curl --delay 1000      # space requests 1s apart
python -m src.cli run --curl-file request.curl --no-pause-on-rate-limit  # headless: warn only
```

> **Warning:** `scripts/rate_limit_test.py` and `scripts/lockout_test.py`
> deliberately hammer endpoints. Never run them against production or
> any WAF-protected host.

## Test Case Bank

`test_cases/default_test_cases.xlsx` is the editable test bank. It is generated by `python -m src.cli seed-test-cases` (or the GUI "Seed Test Cases" button).

## Built-in Universal Suite

The engine **always** runs a built-in universal suite (`src/test_cases_builtin.py`) for every API, regardless of the bank. These are the permanent check points (W1–W14):

- **Contract (W1)**: HTTP 2xx + business error in body → `DEFECT`
- **Baseline (W3)**: GLB-003 — valid request returns expected success code
- **Query params (W4)**: GLB-004/005/006 — invalid values, SQL injection
- **Method (W5)**: GLB-007 — unsupported method → 405
- **Mass assignment (W6)**: GLB-008 — hidden keys sent, response reviewed
- **NoSQL (W7)**: VAL-018 — operator-object injection
- **Security headers (W8)**: GLB-009 — CSP/HSTS/X-Content-Type-Options
- **CORS (W9)**: GLB-010 — evil Origin must not be reflected
- **Sensitive data (W10)**: GLB-011 — no passwords/tokens/OTP in responses
- **Error leak (W11)**: GLB-012 — no stack traces in errors
- **Schema (W12)**: GLB-013 — response matches the declared schema
- **SLA (W13)**: GLB-014 — response within `sla_seconds`
- **Duplicate submit (W14)**: GLB-015 — identical payload submitted twice
- Plus HDR-001…005 (auth/Content-Type) and VAL-001…018 (payload-key mutations)

A supplied bank is merged in and deduped by `test_case_id` — **built-in entries win**, so these checks can never be removed or disabled through the bank. Checks that genuinely don't apply are reported as `Skipped / N/A` rows (no body, public endpoint, endpoint without query params, schema not declared).

## CLI Reference

| Command | Description |
|---------|-------------|
| `run` | Run full test suite against an API endpoint |

### `run` options

| Option | Description |
|--------|-------------|
| `--curl` | Inline curl command string |
| `--curl-file` | Path to file containing curl command |
| `--crypto-profile` | Path to crypto profiles YAML |

| `--test-cases` | Path to test cases xlsx (default: `test_cases/default_test_cases.xlsx`) |
| `--output, -o` | Output report path (default: `reports/report.xlsx`). A file in single mode; a directory in batch mode (`--curl-dir`) |
| `--delay` | Delay between requests in ms (default: 200) |
| `--timeout` | Request timeout in seconds (default: 30) |
| `--settings` | Path to settings YAML (default: `config/settings.yaml` if present) |

| `--include-non-mandatory` | Also test payload keys not detected as mandatory |
| `--response-profile-name` | Separate crypto profile for response decryption |
| `--no-pause-on-rate-limit` | Headless: don't pause on 429/IP-block responses; warn and continue (see [Rate Limits & IP Blocks](#rate-limits--ip-blocks)) |

## How It Works

1. **Parse**: The curl command is parsed into a structured request (method, URL, headers, body, params).
2. **Baseline**: The original request is sent as ground truth.
3. **Header Tests**: All header-scope test cases (missing/invalid headers, auth token variations) run.
4. **Mandatory Detection**: For each payload key, remove it and resend. If the API rejects it → the key is mandatory.
5. **Payload Tests**: Validation/vulnerability test cases run against all mandatory keys.
6. **Report**: Results written to an Excel file with conditional highlighting.

## Crypto Profiles

Configured via YAML. Supports:

- **Algorithms**: AES-256-CBC, AES-256-GCM, AES-128-CBC
- **Key derivation**: PBKDF2HMAC or raw key
- **Output encoding**: base64 or hex
- **IV**: random generation or literal value

Example profile:

```yaml
profiles:
  - name: default
    algorithm: AES-256-CBC
    key_derivation: PBKDF2HMAC
    hash: SHA256
    iterations: 10000
    key: "my-secret-api-key-12345"
    key_encoding: utf8
    salt: "fixed-salt-value"
    output_encoding: base64
```

When no profile is provided, the adapter runs in **pass-through mode** (no encryption), so the tool works for plain APIs too.

## Mutations

The `payload_mutator.py` dispatch table covers:

- `remove_key`, `empty_value`, `null_value`
- `alpha_only`, `numeric_only`, `special_chars`
- `max_length_exceed`, `min_length_violate`
- `sql_injection`, `xss_payload`, `oversized_payload`
- `unicode_emoji`, `wrong_type`, `malformed_json` (replaces the entire body with invalid JSON)
- `header_missing`, `header_invalid_value`
- `auth_token_missing`, `auth_token_invalid`, `auth_token_expired`

All mutations support nested JSON via dot-path addressing (e.g., `user.address.zip`).

## API Profiles

Per-endpoint profiles (YAML, in `config/api_profiles/`) declare *how* an endpoint should be tested, not what to expect. The engine uses them to:

- **Skip non-applicable tests** (auth tests on public endpoints, payload/Content-Type tests on bodyless GETs) — skipped rows appear in the report as `Skipped / N/A — reason`.
- **Evaluate against the standard HTTP contract**: invalid payload → 4xx, invalid/expired token → 401, success → 200. When an API hides a rejection behind HTTP 2xx with a business error in the body (`status:0` / `success:0` / error message), the row is flagged `DEFECT` (yellow highlight) — the API violates the contract.
- **Map custom auth codes** (e.g. Benepik returns 403 "account locked" for bad tokens → `auth_rejection_codes: [401, 403]`).
- **Enable response-level checks** (see table below) — each is reported as its own row (`GLB-009` … `GLB-015`).

Example:

```yaml
name: verify-otp
match: "verify-otp"            # URL substring auto-matching
archetype: otp                 # read_list | write | login | otp | export | job | generic
auth_required: true
body_type: checksum            # none | json | checksum
auth_rejection_codes: [401, 403]
sensitive_fields: [otp, password, token]
expected_success_code: 200
query_params: [page, status]   # enables GLB-004/005/006 query-param tests
response_schema:               # enables GLB-013 schema validation
  success: int
  data: list
sla_seconds: 5                 # enables GLB-014 SLA check
idempotency_required: true     # enables GLB-015 duplicate-submit test
idempotency_key: order_ref     # body field the server dedups on (injected with a unique value)
check_security_headers: true   # default; GLB-009 CSP/HSTS/X-Content-Type-Options
```

Response-level checks:

| ID | Check | Profile switch |
|----|-------|----------------|
| GLB-009 | Security headers (CSP, HSTS, X-Content-Type-Options) | `check_security_headers` |
| GLB-010 | CORS misconfiguration (evil Origin) | always |
| GLB-011 | Sensitive data in response | `sensitive_fields` |
| GLB-012 | Error-leak scan (malformed body) | body endpoints |
| GLB-013 | Response schema validation | `response_schema` |
| GLB-014 | Response within SLA | `sla_seconds` |
| GLB-015 | Duplicate submission (idempotency) | `idempotency_required` + `idempotency_key` |

Run with `--profile-dir config/api_profiles`. In batch mode, a profile whose `name` equals the curl file stem wins; otherwise the `match` URL substring is used.

## Report Format

Generated `.xlsx` with columns: `API | Key | TestCase | TestCaseType | Status | Mandatory | StatusCode`.

- **Conditional highlighting**: Vulnerability rows where the malicious payload was **accepted** are highlighted red (actionable signal).
- Auto-filter, frozen header row, reasonable column widths.
- One sheet per endpoint.

## Extending

### Adding a new MutationType

1. Add the name to `MutationType` enum in `models.py`.
2. Write a mutation function in `payload_mutator.py`.
3. Add to `MUTATION_DISPATCH` dict.
4. Add corresponding test case rows to the xlsx.
5. (Optional) Add `import` reference in `is_header_mutation` if it's a header mutation.

### Adding a new crypto algorithm

1. Add to `Algorithm` enum in `models.py`.
2. Implement encrypt/decrypt logic in `crypto_adapter.py`.
3. Write round-trip unit tests.

## Curl Parser Decision

The tool uses a **custom shlex-based parser** (not `uncurl`) because:
- `uncurl` struggles with multi-line curls containing `\` continuations
- `uncurl` has issues with `--data-raw`, `--data-binary`, and multiple `-H` flags
- Custom parser provides full control and predictable behavior

## Out of Scope (v1)

- No multipart/form-data file upload testing
- No GraphQL support (REST/JSON only)
- No parallel/concurrent execution — sequential only
